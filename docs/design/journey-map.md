## 1. Scope and honesty

- **Covers:** the console at `/` (project list plus one open project), the check-screen builder and operator pages, and every JSON route those pages call (`urls.py` is the route list: `urls.py:7` to `urls.py:174`, plus `urls.py:177` and `urls.py:178` at the end).
- **Does not cover:** the SDK and CLI, and the internals of the `/access` screen (`urls.py:10`) beyond where it touches the journey.
- **What "complete" means here:** the code path exists and is wired from screen to database for image projects. It says nothing about real-world performance. `PRODUCT.md` separates the "available web slice" (sign-in, roles, projects, image import, manual boxes, queued auto-labelling with review) from items that are "present as a prototype (synthetic data and a toy model only)": snapshots and export, CPU training, check screens, stored feedback (`PRODUCT.md:52`). I follow that split in the Status column.
- **Not measured anywhere in the product:** accuracy on real imagery, auto-label accuracy, the feedback-to-new-model path with real operators (`PRODUCT.md:52`, `docs/guides/improve-loop.md:3`).
- **The "9 steps" are the plan's wording.** The console itself shows a **7-step** checklist (`console.js:5609`); see 2.3 for how the two line up.

## 2. Journey table

### 2.0 Legend

- **Min. role** is the lowest role the server accepts for the write named. Every GET is "Viewer" (any signed-in user) unless the table says otherwise (`permissions.py:240` makes `GET` default to view). Ladder: Viewer < Labeler < Trainer < Approver (`permissions.py:36`, `permissions.py:49`; the role table in prose: `docs/guides/access-roles.md:10`). A role may be set console-wide or replaced on one project (`permissions.py:118`, `models.py:713`). A signed-in person in none of the four groups counts as **Labeler** by default (`athena_web/settings.py:145`, `permissions.py:13`).
- **Status words:** `complete` = wired end to end in source for image projects and listed as available in `PRODUCT.md` (`PRODUCT.md:52`); `prototype` = wired, but `PRODUCT.md`/docs call it a prototype tested on synthetic data and a toy model; `unavailable` = no tool in source; `depends on optional worker` = the step stalls without a separate process (`autolabel_worker`, `train_worker`, `inference_worker`).
- **Panel ids** are element ids in `console.html`. Panels are shown one at a time (`console.js:5587`).

### 2.3 Notes that cut across the steps

- **The checklist has 7 steps, not 9.** `checklistSteps` returns: Add pictures (`console.js:5625`), Define labels (`console.js:5631`), Draw or auto-suggest boxes (`console.js:5637`), Review the boxes (`console.js:5646`), Make a training set (`console.js:5655`), Teach the computer (`console.js:5665`), Set up the check screen (`console.js:5676`). The web side learns that a worker is alive from a heartbeat kept in the Django cache with a 45 second lifetime (`training/lifecycle.py:35`, `training/lifecycle.py:89`) on a file-based cache (`athena_web/settings.py:115`), and passes it to the page as `worker_online` (`autolabel_views.py:84`).
- **Access is fail-closed:** a view without a declared role is refused with 403 (`middleware.py:43`).

## 3. Where the user must switch panels or remember something

Each item is a fact in the code; whether it hurts a real user is not established here.

**Navigation state**

1. **One panel at a time.** The workspace is paged (`console.js:5587`); `syncPanels` marks one panel current (`console.js:5906`) and the stylesheet hides the rest (`console.css:779`); the order is fixed by `PANEL_ORDER` (`console.js:16`). The jump bar (`#jump-nav`, `console.html:74`) hides itself unless at least two panels exist (`console.js:5957`); its links look like `#anchors` but clicks are intercepted (`console.js:5965`).
2. **Back and Next skip the home panel and the ends.** "Get started" gets no Back or Next row (`console.js:5922`); Next appears on every other panel except the last (`console.js:5932`). `PANEL_ORDER` runs Labels then Pictures (`console.js:16`) while the checklist runs Pictures (`console.js:5625`) then Labels (`console.js:5631`).
3. **The open panel is not remembered.** The address stores only `#project=<id>` (`console.js:144`); the panel variable starts at "Get started" (`console.js:17`) and is reset when a different project opens (`console.js:155`). Reload, or coming back from the check-screen builder (its link is `/#project=<id>`, `checkscreen_builder.html:4`), lands on "Get started", not on Check screens.
4. **Hash handling is one-shot.** The hash is read once at load (`console.js:314`); no `hashchange` or `popstate` handler exists (searched `console.js`: the only history call is the `replaceState` at `console.js:144` and one more on project delete). Editing the hash by hand does nothing. An unknown or deleted id silently opens the first project (`console.js:317`), which is the newest because the list is ordered newest first (`views.py:101-111`).
5. **The operator page has no way back to the project.** `checkscreen.html` fills only the content and scripts blocks (`checkscreen.html:4`); the base template's `barnav` block is empty (`checkscreen_base.html:19`). The builder does have "All projects" (`checkscreen_builder.html:4`).
6. **Two steps leave the console page.** Checklist step 7's "Set up the check screen" is a link that leaves the page, not a button (`console.js:5683`, `console.js:5792`); the check-screen list's "Open the screen" and "Edit" are page navigations too (`console.js:5512`).

**Checklist gating**

7. **States are computed from counts, not from freshness.** Step 3 is blocked until there are pictures and labels (`console.js:5622`, `console.js:5638`); step 4 until a box exists (`console.js:5647`); step 5 until an accepted box exists, and it stays "done" once **any** snapshot exists, even if boxes changed afterwards (`console.js:5656`); step 6 is done only when a model is approved, training alone never ticks it (`console.js:5666`); step 7 is done only when a switched-on screen has a model in use (`console.js:5618`, `console.js:5677`), and the screen list is `null` until it has loaded (`console.js:5498`). "Do this next" marks the first to-do (`console.js:5825`). The "Every step is done" text keys off the first six (`console.js:5830`).
8. **Blocked steps say "finish steps N first" but have no button.** For example step 5 (`console.js:5655-5665`); the person has to go to the named panel themselves.
9. **Checklist buttons switch panels first** (`scrollAndFocus` calls `showPanel`, `console.js:5597`), but "Open a picture" and "Review suggestions" open the modal while the "Get started" panel stays current (`console.js:5643`). Closing the modal reloads the picture list (`console.js:1380`) and that refreshes the dataset, training, check-screen and corrections data too (`console.js:454`, `console.js:455`).

**Things to carry in the head**

10. **Which snapshot teaching uses.** The main Teach button always sends `snapshot: "latest"` (`console.js:4098`). The snapshot picker is inside the collapsed "Details for your administrator" fold (`console.html:245`, `console.html:258`) and is used only by "Teach with exactly these settings" (`console.js:4153`). "Latest" is reused only if it still holds exactly the current accepted boxes and labels (`training/lifecycle.py:401`); otherwise a **new snapshot with the default 80/10/10 split** is frozen first (`training/lifecycle.py:506`, `training/lifecycle.py:517`) and the page says so afterwards (the plan sentence before the press said "make a saved copy ... first" but did not name the version; the 2026-10-30 redesign added the number) (`console.js:4116`). A custom split chosen in step 5 is therefore used by the main button only while it is still the latest snapshot and nothing has changed since. The picker itself jumps to a newly appearing snapshot (`console.js:3563`).
11. **One thing, three names.** Dataset version (routes and API, `urls.py:58`) = "training set" and "snapshot" (panel text, `console.html:160`) = "saved copy" (Teach panel, `console.js:4484`, and the picker label, `console.html:258`).
12. **Stage names differ from the API.** Stored `staged` is shown as "Ready for trial" (`console.js:3149`) and reached by "Move to trial" (`console.js:4518`); the model's own label is "Staged for review" (`models.py:421`). "Approve for use" stays off until a trial (`console.js:4473`).
13. **Two readiness checks from different sources.** "Is your work ready?" (`console.html:164`) reads `datasets/readiness` (`console.js:2672`); "Are your pictures ready?" (`console.html:212`) reads `datasets/health` and `training/readiness` (`console.js:3921`, `console.js:3936`). Each has its own "Check again" (`console.html:164`, `console.html:243`). Near-duplicate advice appears only in the second (`datasets/health.py:703`).
14. **Unsaved label edits survive a panel switch but their Save button does not.** The guard exists for opening another project (`console.js:148`) and for leaving the page (`console.js:2383`); `showPanel` has no check (`console.js:5896`), and the unsaved note lives inside the Labels panel (`console.html:101`).
15. **Auto-suggest controls sit in Pictures but also drive the dialog.** The strictness select there sets the per-picture suggestion in the modal (`console.js:2040`). The "suggest after upload" tick is cleared by every upload (`console.js:1693`, `console.html:120`).
16. **Corrections have no panel of their own.** They are found in Pictures: a count on the jump link (`console.html:77`), a checklist row (`console.js:5846`), and `openCorrections`, which switches panel (`console.js:501`).
17. **Approval reaches into another panel.** Check screens that use the model being replaced stop working unless they are switched at approval time (`console.js:5086`, `training_views.py:361`); afterwards the person has to look in Check screens for the "Not working" state (`console.js:5506`).
18. **Role is shown in two ways and changes with the project.** The role strip is reworded per project (`console.js:291`, `ui_common.js:300`); controls are switched off with a reason rather than hidden (`ui_common.js:155`, and for models `console.js:4458`).

## 6. Known gaps and dependencies

- **Rights are not enforced or recorded.** `Asset` has no rights field (`models.py:39`); the Pictures panel says the pictures "have not been checked for usage rights" (`console.html:155`); `web/README.md` says the same of snapshots (`web/README.md:105`); `PRODUCT.md` lists rights review as unimplemented (`PRODUCT.md:27`).
- **Every signed-in person sees every project.** The list endpoint returns all projects (`views.py:280`, `views.py:101`); `Project` has no owner or member field (`models.py:23-30`). A role given on one project limits who may **change** it, not who may see it (`web/README.md:83`, `docs/guides/access-roles.md:243`); hiding a project is listed as not implemented (`web/README.md:99`).
- **Default role is Labeler.** A signed-in person in no group acts as a Labeler unless `ATHENA_UNASSIGNED_ROLE=viewer` (`athena_web/settings.py:145`, `permissions.py:61`): they can create projects, upload, label, export snapshots, run check screens and record feedback, but not teach, approve or roll back (`permissions.py:49`).
- **Second-person approval is off by default** (`athena_web/settings.py:149`, `permissions.py:66`).
- **Near-duplicate pictures are a warning, never a stop.** They are added to `advice` (`datasets/health.py:703`); `ready_to_teach` follows blockers only (`datasets/health.py:501`). Byte-identical files are kept in one split (`datasets/health.py:668`). The method has "only been tried on generated pictures" (`datasets/health.py:22`), and the README lists blocking on near-duplicates as not implemented (`web/README.md:99`).
- **Kinds of file other than pictures have no workspace.** The create dialog says "no labelling tools yet" (`console.html:370`); the project table says the same (`console.js:101`); the checklist shows one "Coming soon" row (`console.js:5820`); the Pictures, snapshot, Teach and check-screen panels stay hidden (`console.js:375`); the server answers 400 or 404 on image-only routes (`views.py:507`, `dataset_views.py:26`, `api_common.py:31`); "What you can do today" lists them as "Coming soon" (`console.html:355`).
- **No real scanner connectors in the console.** `PRODUCT.md` says only reference folder and HTTP connectors exist (`PRODUCT.md:52`). A check screen takes one picture a person sends (`inference_views.py:125`). A route or screen for connecting a data source: **not found in source** (`urls.py` lists none).
- **Three worker processes the page cannot start.** A queued training run waits when no worker runs (`training/lifecycle.py:196`), counts as the project's one active run (`training/lifecycle.py:371`), and is not failed by the stale-run sweep, which looks only at runs that were running (`training/runner.py:70`); a Trainer has to cancel it (`training_views.py:274`). Check-screen pictures and auto-suggest jobs likewise wait for their worker (`management/commands/inference_worker.py:48`, `management/commands/autolabel_worker.py:62`).
- **Everything quantitative is synthetic or unmeasured:** no accuracy on real imagery, no auto-label benchmark (`PRODUCT.md:52`); the improve loop has not been run by real operators (`docs/guides/improve-loop.md:3`).
- **Only COCO and YOLO exports** (`datasets/__init__.py:11`).
- **The builder's "Try this picture" writes records** (`checkscreen_builder.html:155`).
- **Deleting a project removes its pictures from disk**, needs only Trainer (`views.py:402-403`, `views.py:395`), and sits as a button in the workspace header (`console.html:72`).
- **Lists are unpaged or capped:** projects (`views.py:280`), pictures (`views.py:510`), snapshots (`dataset_views.py:110`), models and runs (100, `training_views.py:19`), check screens (100, `inference_views.py:20`). The project table shows filters only from 6 projects (`console.js:27`).
- **Deep links reach a project only** (section 3, items 3 and 4); there is no address for a panel, a model, a snapshot or a picture.
