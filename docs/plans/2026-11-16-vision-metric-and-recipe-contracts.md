# Vision metric and recipe contracts

**Status:** T02 implementation specification; a product-level semantic contract, not a Core API/schema or proof that the recipes are implemented. Changes to `contracts/v1` or SDK models still require the RFC process in `CONTRIBUTING.md`.

**Scope:** Define the meaning, prerequisites, compatible inputs, evidence, and missing-data behavior for the first planned people-flow, zone-presence/dwell, estimated-occupancy, and parking workflows. This is the contract future setup, replay, event, aggregate, and dashboard work must implement. Current photo inspection and six-frame video sampling do not satisfy continuous or complete-event prerequisites.

## Shared invariants

1. Every value names its metric, unit, source/view scope, source-time window or observation time, definition/recipe version, completeness state, and update time. Event-derived values also identify the source session and evidence/reference available under the retention policy.
2. Use source/event time for the observation window and ingestion time for freshness/lag. Store timestamps unambiguously (UTC); render site-local windows using an explicit site time zone. Use half-open aggregation windows `[start, end)` so a boundary event is counted once.
3. “Person” and “vehicle” detections are model outputs, not confirmed real-world identities. A track ID is unique only within its camera/source session. Do not deduplicate people across cameras or sessions unless a separately specified and authorized identity capability exists.
4. `0` means the full declared scope was observed with valid evidence and no qualifying objects/events were present. Missing, stale, undecodable, unprocessed, or out-of-scope observations are never silently converted to zero, Free, or an empty interval.
5. Partial values retain their observed numerator and declared denominator/scope, and are visibly marked `partial`. They must not be presented as complete totals. `unknown` has no numeric value for the affected metric and carries a reason.
6. Coverage is evidence about input/process/scope completeness, not detector accuracy, recall, precision, or the probability that an event was counted correctly. Model scores and business-outcome metrics remain separate.
7. Every emitted event/state transition is traceable to the source-time evidence and pinned source view, geometry, recipe/rule, and model version. Reprocessing/retries must not double-count an event.

## Metric definitions

| Metric | Definition and unit | Preconditions | Counterexample / non-meaning |
|---|---|---|---|
| **Entries** | Number of valid directional crossing episodes from the configured outside side to inside side during a named source-time interval. Unit: crossing events. | Person detections plus session-scoped tracks; finite, versioned line and direction labels; stable observations on both sides; valid event timestamps; declared entrance scope. | A person visible in a photo is not an entry. Re-detecting the same stationary person on many frames is not many entries. A track ID is not a unique visitor identity. |
| **Exits** | Number of valid episodes across the same configured line in the opposite direction during the same interval. Unit: crossing events. | Same as entries; reverse direction is explicitly configured and tested. | A person facing the camera or disappearing behind an obstruction is not an exit. |
| **Net flow** | `entries - exits` for the same operation scope and half-open time interval. Unit: net crossings. Negative values are valid. | Valid entry and exit event streams with matching scope, time boundaries, and completeness state. | Net flow is not current occupancy, unique visitors, or the number of people visible. For example, 8 entries and 6 exits yield net flow +2, but do not establish that two people are inside. |
| **Visible presence** | Number of distinct currently tracked detections visible inside a configured zone at a particular source time. Unit: people-in-view at that instant. A time series is a sequence of observations, not a unique-person total. | Person detector and camera-session tracker; versioned zone polygon; a specific observed timestamp. | Summing per-frame presence values does not count visits or unique people. A still image cannot establish who is outside the camera view. |
| **Dwell** | Elapsed source time between a confirmed zone-entry observation and a confirmed zone-exit observation for one tracked visit. Unit: seconds per visit, with aggregate statistic named (for example median or percentile). | Person detections/tracks, versioned zone, source timestamps, and declared maximum observation gap. Visits cut by the requested window or lacking confirmed entry/exit are marked left-/right-censored and are not reported as completed dwell durations. | Current queue size is not dwell. Time between two sparse still samples is not a measured wait duration. An ID switch or long gap cannot be bridged as if identity were certain. |
| **Estimated occupancy** | Baseline occupancy at a named source time plus cumulative validated entries minus exits across every declared boundary since that baseline, plus explicitly attributed adjustments. Unit: estimated persons currently inside the declared site/zone. | Verified baseline, complete inventory of relevant ingress/egress boundaries, valid directional events, synchronized source-time windows, and complete coverage of each required boundary. | A single entrance's net flow is not building occupancy when there are unmonitored doors. Never clamp impossible values to zero/capacity or imply exactness; mark the estimate unknown and report the inconsistent evidence. |
| **Bay status** | Latest confirmed state for each stable, enabled bay: `Free`, `Occupied`, or `Unknown`; `Disabled` is a configuration state, not an observed occupancy. Include `observed_at` and, where known, `changed_at`. | Versioned bay polygons/IDs, compatible vehicle detector plus validated bay-matching rule or a validated per-bay classifier, temporal confirmation policy, and usable source evidence. | A vehicle box overlapping several bays does not establish all of them as occupied. Unknown is not Free. Disabled bays are excluded from usable-capacity totals and shown separately. |
| **Bay availability** | Count of enabled bays confirmed `Free` at the stated time. Unit: bays. Report enabled capacity and unknown count alongside it. | Bay status is current for the declared scope; no stale or missing bay is silently omitted. | `Free / (Free + Occupied)` is not availability if Unknown/Disabled bays were excluded without showing their counts. |
| **Coverage** | A declared completeness measure with an explicit numerator, denominator, scope, and interval. It is not a standalone accuracy score. Report source availability, processing coverage, view/scope coverage separately when they differ. | An explicit expected input schedule/sample policy, declared entrances/bays/zones, and records of source and processing gaps. | “Camera online 99%” does not prove every crossing was visible or detected. A scalar percentage without its denominator and covered scope is not meaningful. |

### Coverage dimensions

- **Source availability:** expected source-time duration with valid frames received divided by expected source-time duration. Exclude scheduled downtime only when it is explicitly configured and shown.
- **Processing coverage:** expected frames/time slices successfully decoded and processed under the recipe's declared sampling policy divided by the expected frames/time slices. A dropped frame or queue gap is recorded, not inferred to be empty.
- **View/scope coverage:** whether all required entrances or enabled bays/regions are configured and observable for the interval. Report uncovered/missing sources by name; do not hide them in a global percentage.
- **Event completeness:** `complete` only when every required boundary is assigned and source/processing/view coverage meets the recipe policy for the interval. This is not a claim of perfect model detection; replay comparison and held-out evaluation measure outcome quality separately.

A coverage percentage requires a denominator. If the expected input cadence, active scope, or time window is unknown, show `unknown` coverage with the reason instead of inventing a denominator.

## Recipe contracts

A recipe is a versioned declaration of a business outcome and its valid input/output rules. It must specify: required source modality and timestamps; source/view scope; compatible model task and labels; required tracker/classifier; geometry and direction/state policy; valid event/state conditions; time-window and aggregation rules; coverage denominator; stale/gap thresholds; partial/unknown behavior; evidence/retention references; and the metrics it is permitted to publish. A model is compatible only when its task, labels, adapter, and input format satisfy the recipe; a high detection score alone does not establish recipe compatibility or operational accuracy.

| Recipe | Compatible inputs and model capability | Geometry / rule | Permitted output | Missing or incompatible input |
|---|---|---|---|---|
| **Photo/sampled-frame inspection** | One still image or explicitly sampled still frames; an image-capable model. This is the current inspection class. | Image regions/prompts only; no temporal continuity contract. | Snapshot description and, when supported, a clearly qualified estimate of visible objects in the supplied frame(s). | Do not emit entries, exits, dwell, live state, complete crossing totals, or building occupancy. Six sampled video frames may miss any movement between frames. |
| **People flow** | Recorded video with preserved source timestamps, or a live video stream; compatible person detector and single-camera/session tracker. | Finite directed line; stable-side crossing episode; explicit session, gap, and event-deduplication policy. | Entries, exits, net flow, per-event evidence, and coverage for configured boundaries. | Still/sparse frames, missing timestamps, unsupported person labels, invalid geometry, or gaps that break continuity make the affected interval partial/unknown. A live recipe is unavailable until supervised live ingestion exists. |
| **Zone presence and dwell** | Time-stamped video plus compatible person detector and camera-session tracker. | Versioned polygon zone; explicit presence observation cadence and maximum track gap; entry/exit confirmation. | Point-in-time visible presence; per-visit dwell with censoring/uncertainty; queue size and dwell remain separate metrics. | A snapshot supports visible presence only. No timestamps means no dwell. Long occlusion, tracker reset, or stale frames censors/invalidates the affected visit; never bridge it as a complete visit. |
| **Estimated building occupancy** | All required people-flow boundary streams plus source-time events; no additional identity model can substitute for missing entrances. | Explicit site boundary/entrance inventory, direction per entrance, timestamped baseline, adjustment/reconciliation policy. | Baseline-derived occupancy estimate and its completeness/uncertainty. | Missing baseline, undeclared/unmonitored door, incomplete coverage, incompatible timestamps, or impossible arithmetic makes occupancy unknown; valid per-door counts may still be shown as partial. |
| **Parking bay state** | Time-stamped video plus compatible vehicle detection and validated bay association, or a validated per-bay state classifier. | Stable named bay polygons; explicit assignment/overlap policy; temporal confirmation/debounce; stale timeout. | Per-bay Free/Occupied/Unknown, changed/observed times, free count, capacity, unknown count, and coverage. | A still may support only a qualified snapshot; it cannot support continuous state or transition timing. Missing feed, obscuration, ambiguity, stale state, or absent calibration yields Unknown, not Free. |

No recipe in this document asserts a production-ready model, deployed live source, or real-world accuracy. Live input contracts are prospective until the live source/runtime and recovery tasks pass their own gates.

## Missing-data and output-state contract

Every metric result has exactly one completeness state for its declared scope and interval:

- **`complete`:** all required inputs and scope were configured and valid; source and processing coverage met the recipe policy; the value is meaningful for the whole interval. A valid observed zero is allowed.
- **`partial`:** some valid evidence exists, but one or more inputs, frames, boundaries, or intervals are missing or out of policy. Preserve the observed value only with its observed scope and gap details; do not label it as the full-scope total.
- **`unknown`:** prerequisites are absent or the available evidence cannot support even a scoped numeric result. Return no numeric value for that metric and include a reason.

Minimum reason codes for implementation: `not_configured`, `unsupported_input`, `source_offline`, `stale_input`, `decode_error`, `processing_gap`, `scope_incomplete`, `geometry_invalid`, `model_incompatible`, `timestamp_unreliable`, `baseline_missing`, `ambiguous_assignment`, and `insufficient_evidence`. A specific code may accompany `partial` or `unknown` as appropriate. The UI must show the last observed/processed time and affected scope when stale or incomplete.

Examples:

1. One complete clip shows two valid entries and one exit through a configured door. Return entries `2`, exits `1`, net flow `+1`. Do not call this one net-new identified person or current occupancy.
2. A zone contains three tracked people at 10:00:00. Return visible presence `3 at 10:00:00`. If their visits span 30, 60, and 90 seconds, report those completed dwell values separately; the visible count is not the number of visits.
3. A site baseline is 12 people; complete, gap-free streams show 2 entries and 3 exits across every boundary. Estimated occupancy is 11 for that interval. If a declared service exit has no source, occupancy is `unknown` (or partial only if the interface explicitly labels a bounded observed-scope result); do not present 11 as whole-building occupancy.
4. A site has five enabled bays: three confirmed Free, one Occupied, one Unknown. Report free `3`, enabled capacity `5`, unknown `1`; availability is not `3/4`. If one bay is Disabled, display it separately and exclude it from enabled capacity.
5. A parking photo shows three apparently empty bays. It can produce a qualified photo observation, not a live Free state or an availability trend. Six frames sampled from a short clip cannot produce a complete crossing or dwell total.

## Implementation gates and exclusions

- T02 supplies product semantics for later contracts and UI. It does not add database fields, API responses, inference/training behavior, model adapters, or a JSON Schema.
- T08 must validate model/source readiness against these recipe prerequisites. T14–T18 implement/version geometry; T19–T24 provide timestamps, tracking, event storage and coverage; T25–T31 implement event, occupancy and bay rules; T40–T42 expose uncertainty and metrics. Each task retains its own acceptance evidence.
- Do not expose a metric in a board or export unless the operation has a compatible recipe, authorized scope, valid required inputs, completeness state, and definition/version. Unsupported recipes should be unavailable, not a wizard path that silently substitutes photo interpretation.
- Keep queue length, visible presence, visit count, dwell, entries/exits, net flow, and occupancy as distinct metrics. Do not combine model confidence, source coverage, event-comparison error, and business totals into one score.
